Para Jesica y Agustín: cómo sumar la «App perfil directivo neon» al sistema común

Revisamos la versión que subieron el 06/11/2026 (commits 814a520 y 5be26e8). Las pantallas están muy bien. Lo que hay que cambiar es por dónde entran y adónde van los datos. Esta nota dice qué, por qué y en qué orden.

0.Lo primero, hoy

¿A qué base de Neon conectaron el proyecto de Vercel de esta app?
La app usa la variable DATABASE_URL, la misma que usa la API común. Si apunta a la base del sistema (neondb), la app le está creando tablas sueltas (institution_state, app_accounts, app_sessions, app_login_attempts) al lado de las nuestras, con cuentas que no son las del sistema.
  • Avísennos a qué base está conectada.
  • No borren tablas ustedes. Si están en la base común, las sacamos nosotros con respaldo previo.
  • Si para eso alguien les pasó la cadena de conexión de la base común, avísennos también: hay que cambiar esa contraseña.
  • Hasta que lo resolvamos, no carguen datos reales en esta app.

1.Lo que está bien y se queda

El diseño

Usa la misma paleta institucional que el sistema (#14214F, #89743A, #AF9B63). Se mantiene.

Las pantallas

Tablero, usuarios, cursos, asistencia, notas, horarios, comunicados, informes, auditoría y configuración. Son exactamente lo que tiene que tener Directivos.

Impresión y CSV

El boletín, las circulares con membrete y la exportación a Excel se quedan. Solo cambia de dónde salen los datos.

Cuidado con la seguridad

Contraseñas con hash, cookies HttpOnly, bloqueo tras 5 intentos. Es lo mismo que ya hace la API común, así que no hace falta repetirlo.

2.Los cuatro problemas

a) Login y cuentas propias

La app tiene sus propios usuarios y contraseñas. El sistema ya tiene uno solo para todas las apps (/api/v1/auth/login), y Directivos es justamente quien crea esas cuentas para alumnos, docentes, preceptores, Centro y Auxiliares. Con dos juegos de cuentas, la cuenta que crea Directivos no le sirve a nadie.

b) Todos los datos en un solo «cajón»

/api/state guarda todo el estado de la app como un único JSON (institution_state.payload) y lo reemplaza entero en cada guardado. Las otras apps no lo pueden leer, dos personas guardando a la vez se pisan, y no se puede auditar quién cambió qué. El sistema tiene una tabla por cosa (alumnos, comisiones, asistencia, notas…) y una ruta para cada una.

c) Modelo de secundaria

La app usa divisiones, trimestres, período de intensificación (diciembre–febrero) y familias. El instituto es terciario: carreras, planes, materias que se dictan en comisiones, cuatrimestres, parciales, recuperatorios y finales.

d) Datos que se van del sistema

El respaldo a Google Drive desde el navegador (con Firebase) y el respaldo en localStorage sacan datos personales de alumnos fuera de la base. Los respaldos se hacen de Neon, del lado del servidor.

6.En qué orden hacerlo

  1. Responder la pregunta de la sección 0 (a qué base está conectada) y frenar la carga de datos reales.
  2. Levantar la API común en local: en la raíz del repo, npm run dev:api (puerto 4000). Para Directivos conviene trabajar directo contra ella: casi todo lo que necesitan ya existe, así que no hace falta una base propia.
  3. Armar la capa de API en src/api/: un client.ts con la dirección base, y un archivo por grupo (users.ts, structure.ts, attendance.ts, records.ts). Pueden copiar los tipos de shared/types.ts y las funciones de shared/api.ts del repo.
  4. Cambiar el login por /auth/login + /auth/me, y sacar el selector de rol.
  5. Pasar pantalla por pantalla de AppContext a la capa de API, en este orden: usuarios → cursos y matrícula → configuración → comunicados y calendario → asistencia y notas (lectura) → informes y auditoría.
  6. Anotar en PROPUESTAS.md lo marcado como propuesta (EOE, vicedirección, situación de revista, rectificación de notas, solapamientos, alerta temprana, datos de la institución, familias). Usen el prefijo P-DIR-.
  7. Sacar lo de la sección 5.
  8. Dejar el CHANGELOG con lo hecho y lo que no probaron.
Las reglas generales (nombres, formatos, errores, cómo proponer cosas nuevas) están en docs/CONTRATO_UNIFICACION.html del repo. Esta nota es lo específico de su app.

7.Texto para pegar en las instrucciones de su agente

## Integración con el sistema común (obligatorio)

Esta app es el panel de Directivos del Sistema de Gestión i26. NO tiene base ni
login propios: usa la API común /api/v1 (backend/ en la raíz del repo, en local
con `npm run dev:api` en el puerto 4000).

Antes de cambiar algo, leé docs/CONTRATO_UNIFICACION.html y
docs/NOTA_DIRECTIVOS_UNIFICACION.html.

- Login: POST /auth/login, GET /auth/me, cookie sga_session, credentials:'include'.
  El rol sale de la sesión; no hay selector de rol.
- Datos: /users, /structure/*, /attendance/*, /records/* (ver la tabla de la nota).
  Nada de /api/state, institution_state, app_accounts ni DATABASE_URL en esta app.
- Modelo terciario: carrera, plan, materia, comisión, ciclo. Sin divisiones ni
  trimestres. Códigos en inglés (DIRECTOR, PRESENT, MORNING…); castellano en pantalla.
- "Ausente justificado" = ABSENT + Justification APPROVED.
- Toda llamada al servidor va en src/api/. localStorage solo para preferencias.
- Sin Google Drive ni Firebase: no sacar datos de alumnos del sistema.
- Lo que no exista en la API se anota en PROPUESTAS.md (prefijo P-DIR-) y se
  marca "// PROPUESTA directivos: motivo". No se inventan rutas ni tablas.
- Al terminar: CHANGELOG.md con lo hecho y lo que no se probó.
