Por qué las cuentas siguen solo en Administración. Crear una cuenta es dar acceso al sistema. Preceptoría carga la ficha del alumno o del tutor; el acceso lo habilita Dirección o Administración. Así una sola área es responsable de quién entra.

3.En qué orden se carga la institución

Cada paso necesita el anterior. Es el orden que tiene que seguir la pantalla.

  1. Carrera. POST /structure/careers → { code, name, durationYears }
  2. Plan de estudios de esa carrera. POST /structure/plans → { careerId, code, name, startYear }
  3. Materias del plan, con su año y su cuatrimestre. POST /structure/subjects → { planId, code, name, year, period, weeklyHours }. period es FIRST_TERM, SECOND_TERM o ANNUAL.
  4. Ciclo lectivo (una vez al año). POST /structure/cycles → { year, startDate, endDate, firstTermEndDate }. Nace en PLANNED: se activa aparte con PATCH /structure/cycles/:id → { "status": "ACTIVE" }, y eso cierra el ciclo que estaba activo (queda uno solo).
  5. Docentes. POST /structure/teachers → { fileNumber, dni, firstName, lastName, email, phone, title }
  6. Curso (comisión): es la materia dictada este año, en un turno, con su horario y sus docentes. POST /structure/commissions → { code, cycleId, subjectId, period, shift, teacherIds, preceptorUserId, schedule, capacity }
  7. Alumno. POST /structure/students → { fileNumber, dni, firstName, lastName, email, phone, careerId, planId, admissionDate }
  8. Inscripción del alumno al curso. POST /structure/enrollments → { studentId, commissionId }. Sin esto, el alumno no figura en la planilla de asistencia.
  9. Cuentas (Administración): del alumno, del docente y del tutor. POST /users → { email, firstName, lastName, roles }. Devuelve una clave temporal y obliga a cambiarla al entrar.
  10. Padre o tutor: con la cuenta ya creada (rol GUARDIAN), se carga su ficha y se le asignan los hijos. PUT /families/guardians/:userId → { dni, phone, address, occupation, children: [{ studentId, relationship }] }. relationship es MOTHER, FATHER o LEGAL_GUARDIAN.

4.Por qué se ve en todos los paneles

No hay copias ni sincronización: hay una sola base y una sola API. Cada panel pregunta lo mismo.

Preceptoría ─┐
Dirección ───┤                 ┌─ Profesores: sus cursos y su planilla
Profesores ──┼→ API /api/v1 ──→│─ Alumnos: sus materias, su asistencia, sus notas
Alumnos ─────┤   (una sola)    │─ Familias: lo de sus hijos
Familias ────┤       │         └─ Centro y Auxiliares: lo suyo
Centro ──────┘       ▼
              PostgreSQL (Neon)

Ejemplo real. Preceptoría carga la carrera, la materia, el curso del miércoles de 18 a 20 con su profesor, el alumno y su inscripción. Sin que nadie copie nada:

  • el profesor ve ese curso y al alumno en su planilla (/academic/scope, /attendance/...);
  • el alumno ve la materia y su horario en su panel (/me/subjects);
  • el tutor ve a ese chico y su asistencia (/guardian/children);
  • la dirección lo ve en estructura y en los informes.
Un solo cálculo de asistencia. El porcentaje lo hace la API con los parámetros de la institución (mínimo 75 %). Preceptoría, el profesor, el alumno y la familia ven el mismo número porque ninguno lo calcula por su cuenta.

6.Datos de prueba

La base quedó limpia para empezar a cargar la institución de verdad.

  • Se dieron de baja los datos de ejemplo (carreras, alumnos, comisiones, asistencias y justificaciones de demostración) y las cuentas de prueba.
  • Quedan solo las cuentas institucionales reales y la configuración de la institución.
  • Los datos de ejemplo se pueden volver a cargar en cualquier momento para una demostración, pero no en la base real: para eso está la base de prueba local.
Importante antes de cargar datos reales. Una vez que entren alumnos de verdad, la base tiene datos personales de menores y de familias. Desde ese momento: respaldo antes de cada cambio de base, y nada de copiar la base a una computadora personal ni a un Drive.
