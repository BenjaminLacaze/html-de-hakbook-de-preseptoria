1. Introducción

El presente informe comunica el estado de avance del desarrollo del Sistema Profesor, un módulo de un Sistema de Gestión Académica (SGA) destinado a facilitar las tareas cotidianas de los docentes dentro de una institución educativa.

El proyecto se encuentra en la etapa de análisis, diseño conceptual del dominio y planificación técnica. Durante esta fase se trabajó en la definición del alcance funcional, la identificación de las entidades principales, el análisis de las reglas de negocio y la evaluación de una arquitectura que permita desarrollar el módulo de manera organizada, mantenible y preparada para su futura integración con otros componentes del sistema académico.

La estrategia consiste en avanzar progresivamente, validando cada etapa antes de implementar la siguiente. Se busca reducir errores de diseño, evitar decisiones prematuras y mantener una separación clara entre las reglas propias del módulo y las responsabilidades de los sistemas institucionales externos.

2. Objetivo general

Diseñar e implementar un módulo web que permita a los docentes consultar sus comisiones y materias asignadas, acceder a las nóminas de alumnos, registrar la asistencia, consultar su historial y registrar observaciones académicas, respetando los permisos correspondientes y las reglas de negocio definidas para el sistema.

3. Alcance funcional del MVP

Se definió un producto mínimo viable (MVP) compuesto por seis funcionalidades principales:

  1. Acceso del profesor: permitir que el docente ingrese mediante el mecanismo de autenticación que se determine para la integración institucional.
  2. Consulta de comisiones y materias: mostrar las comisiones y materias asignadas al docente durante el período lectivo correspondiente.
  3. Consulta de alumnos: visualizar la nómina de alumnos pertenecientes a una comisión a la que el docente esté asignado.
  4. Registro de asistencia: registrar los estados presente, ausente y tarde para los alumnos de una instancia de clase.
  5. Historial de asistencia: consultar los registros históricos de asistencia de un alumno dentro de las comisiones autorizadas, sin modificar registros desde esta funcionalidad.
  6. Observaciones académicas: registrar y consultar observaciones cualitativas asociadas a un alumno, una comisión, una fecha y un docente autor, según los permisos que se definan.

El alcance inicial excluye la gestión de calificaciones, los comunicados a comisiones y la carga de archivos adjuntos. Estas funcionalidades podrán evaluarse en etapas posteriores, una vez que el MVP esté implementado y validado.

4. Análisis y diseño del dominio

Antes de comenzar la implementación, se elaboró un modelo conceptual del dominio para identificar los conceptos necesarios para representar las operaciones del módulo.

Entre las entidades y referencias identificadas se encuentran:

  • Profesor, alumno, materia y comisión.
  • Período lectivo y asignación docente.
  • Vínculo temporal entre alumno y comisión.
  • Instancia de clase y registro de asistencia.
  • Observación académica.

Se distinguieron los datos propios del Sistema Profesor de aquellos que deberían ser proporcionados por otros componentes del SGA. Las identidades de profesores y alumnos, las comisiones, las materias y las asignaciones docentes se consideran referencias a datos institucionales externos cuya fuente oficial debe confirmarse. Las observaciones académicas se plantean como información propia del módulo.

La propiedad del registro oficial de asistencia permanece pendiente de definición, ya que depende de cómo se integre el módulo con el sistema central de asistencia.

Decisión de diseño relevante: se diferencia una fecha del calendario de una instancia de clase concreta. Así se pueden representar dos clases de una misma comisión en un mismo día sin confundir sus registros de asistencia.

También se incorporó el concepto de vínculo temporal entre alumno y comisión para contemplar cambios de comisión y preservar la interpretación histórica de los registros.

5. Arquitectura propuesta

Se está evaluando una arquitectura organizada mediante el enfoque de puertos y adaptadores, también conocido como arquitectura hexagonal. El objetivo es separar las reglas de negocio de los detalles técnicos, como la base de datos, la interfaz web y las comunicaciones con sistemas externos.

Frontend

Será la interfaz web utilizada por los docentes. Presentará las pantallas, gestionará las interacciones del usuario y se comunicará con el backend.

Backend

Concentrará las reglas de negocio, las validaciones, los controles de autorización y los casos de uso del módulo. La lógica principal no debería depender directamente de la interfaz web ni de los mecanismos concretos de persistencia.

Dominio

Representará los conceptos, las reglas y las restricciones propias del Sistema Profesor.

Puertos y adaptadores

Permitirán definir interfaces para acceder a servicios externos, como autenticación, datos académicos y asistencia. De esta manera, se podrán desarrollar y probar determinadas funcionalidades con implementaciones simuladas mientras se definen los contratos de integración reales.

Persistencia

La tecnología y la responsabilidad definitiva del almacenamiento deberán ajustarse a los acuerdos sobre la propiedad de los datos. No se considera confirmado que el Sistema Profesor deba almacenar localmente los registros oficiales de asistencia.

Esta arquitectura es una propuesta de diseño y todavía debe confirmarse antes de iniciar la implementación.

6. Tecnologías evaluadas

Se analizaron las siguientes tecnologías como candidatas para el desarrollo:

Componente Tecnología propuesta Responsabilidad
Frontend React + TypeScript Interfaz web y componentes reutilizables.
Backend Python + Django REST Framework API, validaciones y lógica del servidor.
Base de datos PostgreSQL Persistencia relacional, si corresponde al modelo de integración definitivo.
Contratos API REST y OpenAPI Comunicación documentada entre componentes.
Control de versiones Git Seguimiento de cambios y organización del desarrollo.
Pruebas pytest y herramientas apropiadas para frontend Verificación de reglas, casos de uso e integración.

Las herramientas de desarrollo disponibles fueron inspeccionadas y se informó que el entorno cuenta con Python, Node.js, npm y un servicio PostgreSQL instalado. Git también está disponible, aunque todavía queda pendiente inicializar el repositorio del proyecto.

La selección definitiva del stack tecnológico forma parte de las decisiones que deben aprobarse antes de instalar las dependencias y crear la estructura inicial.

7. Seguridad y control de acceso

El diseño contempla que el acceso a la información no dependa únicamente de que un usuario haya iniciado sesión. Se distinguen cuatro aspectos de seguridad:

  1. Identidad: determinar qué usuario está autenticado.
  2. Rol: verificar que el usuario tenga el perfil docente correspondiente.
  3. Asignación académica: comprobar que el docente esté vinculado a la comisión y al período relevantes.
  4. Autorización del recurso: validar que pueda consultar o ejecutar la operación solicitada sobre los datos específicos.

Esta separación es importante para evitar que un docente acceda a información de comisiones que no tiene asignadas. El mecanismo de autenticación y la forma de obtener las asignaciones docentes deben acordarse con los responsables de los sistemas institucionales antes de implementar la integración real.

8. Estrategia de desarrollo

Se decidió trabajar por etapas pequeñas, con objetivos y criterios de aceptación definidos para cada una.

  1. Análisis y documentación: definición del alcance funcional, revisión de la arquitectura y elaboración del modelo conceptual del dominio.
  2. Preparación técnica: confirmación del stack, definición de la estructura de directorios, inicialización del repositorio Git y preparación de los entornos de desarrollo.
  3. Inicialización del proyecto: creación del esqueleto de frontend y backend, configuración de las herramientas básicas y verificación de que ambas partes puedan ejecutarse.
  4. Dominio y pruebas iniciales: implementación progresiva de las reglas de negocio que puedan definirse sin depender de acuerdos externos, con pruebas automatizadas.
  5. Funcionalidades del MVP: desarrollo gradual de las consultas de comisiones y alumnos, asistencia, historial y observaciones, junto con los mecanismos de acceso correspondientes.
  6. Integración y validación: adaptación a los contratos institucionales disponibles, pruebas de integración, revisión de permisos y validación del funcionamiento general.

Las etapas podrán ajustarse según los acuerdos de integración y los resultados obtenidos durante las pruebas.

9. Uso de herramientas de asistencia al desarrollo

Para organizar el trabajo se está utilizando un flujo asistido por herramientas de inteligencia artificial, con responsabilidades diferenciadas. La herramienta de desarrollo se utilizará para ejecutar tareas concretas, generar archivos y realizar cambios en el proyecto. La planificación técnica, la revisión de las decisiones de diseño y la validación de los resultados se realizarán mediante un proceso de revisión humana asistido por IA.

Cada tarea tendrá un alcance definido y deberá informar qué archivos modificó, qué pruebas ejecutó y qué cuestiones quedaron pendientes. No se avanzará automáticamente a la siguiente etapa sin revisar el resultado.

Este enfoque busca utilizar la automatización para agilizar el trabajo, manteniendo el control sobre las decisiones técnicas y la comprensión del sistema desarrollado.

10. Decisiones pendientes

Se identificaron cuestiones que dependen de definiciones institucionales o técnicas todavía no confirmadas:

  • Propiedad y almacenamiento oficial de los registros de asistencia.
  • Política de rectificación de una asistencia registrada.
  • Posibilidad de guardar una toma de asistencia incompleta.
  • Mecanismo para consultar las asignaciones docentes.
  • Fuente y actualización de la nómina de alumnos.
  • Resolución del período lectivo activo.
  • Política de visibilidad de las observaciones entre docentes.
  • Formato de los identificadores compartidos entre sistemas.

Estas cuestiones no impiden preparar el entorno ni desarrollar componentes independientes, pero deberán resolverse antes de cerrar las partes del sistema que dependan directamente de ellas.

11. Estado actual y próximos pasos

A la fecha de este informe, se completaron tareas de análisis documental, evaluación de alternativas arquitectónicas y diseño conceptual del dominio. Se cuenta con documentación sobre arquitectura, decisiones, progreso, planificación y especificación del modelo conceptual.

La versión 1.1 del modelo de dominio incorpora correcciones derivadas de una revisión técnica, entre ellas la posibilidad de registrar asistencia parcialmente, la distinción entre identidad y descripción de una instancia de clase, y la representación temporal de la relación entre alumnos y comisiones.

Estado real del proyecto: la implementación del código de aplicación todavía no comenzó. La inicialización del repositorio, la creación del esqueleto del frontend y backend y la instalación de dependencias siguen pendientes.

Los próximos pasos son:

  1. Confirmar la estructura técnica y aprobar el stack.
  2. Inicializar Git y preparar los directorios del proyecto.
  3. Configurar frontend y backend.
  4. Comprobar que ambos entornos se ejecuten correctamente.
  5. Incorporar pruebas básicas y comenzar con una primera funcionalidad pequeña.
  6. Avanzar progresivamente hacia el MVP, manteniendo documentadas las decisiones pendientes.

12. Conclusión

El proyecto cuenta con una base de análisis y diseño que permite comenzar la implementación de manera ordenada. La principal prioridad en esta etapa es transformar las decisiones conceptuales en una estructura técnica funcional, sin anticipar acuerdos institucionales que todavía no están definidos.

El desarrollo se realizará de forma incremental, con separación de responsabilidades, pruebas y revisión de cada etapa. Se busca obtener un módulo comprensible, mantenible y preparado para integrarse con los demás componentes del Sistema de Gestión Académica.

El objetivo inmediato no es implementar todas las funcionalidades de una sola vez, sino establecer una base técnica verificable y construir el MVP progresivamente, validando tanto su funcionamiento como su adecuación a las necesidades académicas de la institución.
